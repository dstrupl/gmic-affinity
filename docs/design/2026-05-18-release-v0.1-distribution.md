**Date:** 2026-05-18
**Status:** Approved, ready for implementation planning (implementation deferred to a later session).
**Supersedes for distribution:** PRD.md §8 row "Notarised distribution" (notarisation remains deferred but the *release path* is now defined; this design ships **without** notarisation in v0.1).

## 0. Summary

Ship the existing ad-hoc-signed `GmicFilter.plugin` MVP to non-developer
users on Affinity Photo 2 **and** Affinity Photo v3, without enrolling
in the Apple Developer Program for v0.1. Distribute primarily via a
private Homebrew tap so users get a one-liner install
(`brew install --cask dstrupl/gmic-affinity/gmic-affinity`), with a
zipped GitHub release + `install.command` script as the manual
fallback. The two distribution mechanisms ship the **same** universal
zip artifact; only the install glue differs.

The plan is contingent on a small empirical de-risking phase
(Phase 0, §3): we don't yet know whether Affinity Photo v3 loads the
current bundle at all, nor whether a `com.apple.quarantine`-marked
plugin bundle is accepted by Affinity's hardened-runtime loader. The
design covers both outcomes.

Apple notarisation, official `homebrew-cask` submission, and MacPorts
are explicitly deferred (§7).

## 1. Decisions made during brainstorming

| # | Decision                                                                                       | Why                                                                                  |
|---|------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------|
| 1 | Ship as **v0.1.0** (keep current Cargo version)                                                 | Honest signal that this is a first public release; users should expect rough edges.  |
| 2 | **No Apple Developer Program** enrolment for v0.1                                              | $99/yr + per-release notarisation overhead is not justified until usage shows demand. |
| 3 | **Primary channel: private Homebrew tap** (`dstrupl/homebrew-gmic-affinity`)                   | Brew is the dominant macOS package manager; runtime `gmic` dep is already brew-installed; one-liner install for users. |
| 4 | **Fallback channel: GitHub release zip + `install.command`**                                   | Covers users without brew and users for whom path C (quarantined cask) turns out not to work. |
| 5 | **Support both Affinity Photo 2 and Affinity Photo v3** from day one                            | User goal; the underlying plugin protocol is stable across versions (pending Phase 0 verification). |
| 6 | **One artifact for both channels** — a single universal `.plugin` zip                          | Avoids drift between cask install and manual install; one CI build feeds both.       |
| 7 | **Empirical Phase 0** before committing to a specific cask shape                                | Two unknowns (v3 compatibility, quarantine tolerance) gate the design; cheaper to verify in an afternoon than to redesign after a release. |
| 8 | **Cargo-feature gate stays as today** (`FEATURES=live`)                                         | The release ships `FEATURES=live`; the default no-op build remains a safe fallback for developers reconciling SDK changes. |

## 2. Scope: what v0.1 ships

The release contains exactly one artifact:

```text
GmicFilter-v0.1.0.zip
└── GmicFilter-v0.1.0/
    ├── GmicFilter.plugin/        # universal, ad-hoc signed, FEATURES=live
    ├── install.command           # double-clickable installer for manual users
    └── README.txt                # 3-line manual install instructions
```

Two distribution channels share that artifact:

1. **Homebrew (private tap).** New repo `dstrupl/homebrew-gmic-affinity`,
   one cask file. User flow:
   ```bash
   brew tap dstrupl/gmic-affinity
   brew install --cask gmic-affinity   # pulls in gmic too
   ```
2. **Manual install (GitHub release).** User downloads the zip from the
   project's GitHub Releases page, unzips, double-clicks
   `install.command`.

Both produce the same end state: `GmicFilter.plugin` copied into every
Affinity plugin folder that exists on the user's machine
(`~/Library/Application Support/Affinity Photo 2/Plugins/` and/or
`~/Library/Application Support/Affinity/Plugins/`, see §3 step 2).

## 3. Phase 0 — empirical de-risking

Three checks, all manual, ~one afternoon of wall-clock time. None of
the rest of the implementation should start until these resolve.

### Step 1 — Verify v2 still works (regression baseline)

Sanity check that the current `main` build still installs into
Affinity Photo 2 and runs a filter end-to-end. Establishes the
baseline before we change anything.

### Step 2 — Verify the current ad-hoc plugin loads in Affinity v3

User has v3 installed but has never tested the plugin there. Procedure:

1. Find the v3 plugin folder. The strong-prior guess is
   `~/Library/Application Support/Affinity/Plugins`. Confirm by:
   - Looking at `~/Library/Application Support/` for any `Affinity*`
     directory that isn't `Affinity Photo 2`.
   - If unclear, run v3 with `fs_usage` watching for `stat`/`open`
     calls under `~/Library/Application Support/` at startup, the
     same technique used in the original Affinity-2 plugin
     reverse-engineering (see `IMPLEMENTATION_NOTES.md` §2).
2. `make universal-install FEATURES=live AFFINITY_PLUGINS_DIR="<v3 path>"`.
3. Restart Affinity Photo v3 with a 8-bit RGB document open.
4. Confirm `Filters → Plugins → G'MIC → G'MIC...` appears and the
   picker opens.
5. Pick a known filter (e.g. `Artistic / Paint Brush`), OK,
   verify visible transformation.

**If the plugin does not load in v3**, this design's scope changes:
v3 compatibility itself becomes a separate investigation (probable
suspects: `FilterRecord` layout drift between Affinity 2 and 3, PiPL
scanner changes). The release pauses until v3 either loads or is
deliberately dropped from v0.1 scope.

### Step 3 — Quarantine-tolerance test

The empirical question that decides whether path C (brew cask) is
viable:

```bash
# Reproduce what `brew install --cask` will do.
cd /tmp
cp -R "$HOME/Library/Application Support/Affinity Photo 2/Plugins/GmicFilter.plugin" .
xattr -w com.apple.quarantine \
  "0081;$(printf '%x' $(date +%s));Safari;|com.apple.Safari" \
  GmicFilter.plugin
# Verify the bit landed:
xattr -p com.apple.quarantine GmicFilter.plugin
# Reinstall into both Affinity folders.
rm -rf "$HOME/Library/Application Support/Affinity Photo 2/Plugins/GmicFilter.plugin"
cp -R GmicFilter.plugin "$HOME/Library/Application Support/Affinity Photo 2/Plugins/"
# (same for v3 path if verified above)
```

Restart each Affinity version, check whether the plugin still loads.

**Outcomes:**

- **Both load with quarantine bit set** → path C is viable. The cask
  uses `quarantine false` (or accepts the default brew quarantine and
  documents `brew install --cask --no-quarantine` only as a fallback).
- **Either rejects the quarantined bundle** → path C is dead for v0.1.
  We ship only path D (manual `install.command`), and reopen Apple
  Developer enrolment as a v0.2 candidate. The Homebrew tap may still
  exist but will instruct users to `brew install --cask --no-quarantine`
  and clearly explain the trade-off.

A short status note (one paragraph) appended to the implementation

## 4. Build and packaging changes

### 4.1 `make install` learns about Affinity v3

Today:

```makefile
AFFINITY_PLUGINS_DIR ?= $(HOME)/Library/Application Support/Affinity Photo 2/Plugins
```

After: a plural-valued, comma-separated default that installs into
every directory that exists, skipping the rest:

```makefile
# Comma-separated list of Affinity Plugins folders. The install target
# installs into each one that currently exists.
AFFINITY_PLUGINS_DIRS ?= $(HOME)/Library/Application Support/Affinity Photo 2/Plugins,$(HOME)/Library/Application Support/Affinity/Plugins
```

The `install` and `universal-install` targets iterate, `mkdir -p` only
into a directory whose parent exists (i.e. the Affinity app *is*
installed), and skip directories whose parent doesn't.

The legacy singular `AFFINITY_PLUGINS_DIR` keeps working — if set, it
overrides the plural list. This preserves backwards compatibility for
existing developer workflows.

### 4.2 New `make release` target

```makefile
RELEASE_VERSION ?= $(shell git describe --tags --always)
DIST_DIR        := dist
RELEASE_NAME    := GmicFilter-$(RELEASE_VERSION)
RELEASE_ZIP     := $(DIST_DIR)/$(RELEASE_NAME).zip

release: universal
        @rm -rf "$(DIST_DIR)/$(RELEASE_NAME)" "$(RELEASE_ZIP)"
        @mkdir -p "$(DIST_DIR)/$(RELEASE_NAME)"
        cp -R "$(BUNDLE)" "$(DIST_DIR)/$(RELEASE_NAME)/"
        cp install.command release/README.txt "$(DIST_DIR)/$(RELEASE_NAME)/"
        chmod +x "$(DIST_DIR)/$(RELEASE_NAME)/install.command"
        cd "$(DIST_DIR)" && zip -r "$(RELEASE_NAME).zip" "$(RELEASE_NAME)"
        @echo "Built $(RELEASE_ZIP)"
        @shasum -a 256 "$(RELEASE_ZIP)"
```

The `shasum` print is for convenience — the GitHub Actions release
workflow re-computes and embeds it in the cask file automatically.

### 4.3 `install.command`

A new top-level shell script. The whole script:

```bash
#!/usr/bin/env bash
set -euo pipefail

cd "$(dirname "$0")"
PLUGIN="GmicFilter.plugin"
if [[ ! -d "$PLUGIN" ]]; then
  echo "ERROR: $PLUGIN not found next to install.command." >&2
  exit 1
fi

# Strip Gatekeeper quarantine (added if the zip was downloaded via a
# browser). Idempotent: no-op if not set.
xattr -dr com.apple.quarantine "$PLUGIN" 2>/dev/null || true

TARGETS=(
  "$HOME/Library/Application Support/Affinity Photo 2/Plugins"
  "$HOME/Library/Application Support/Affinity/Plugins"
)

INSTALLED=0
for dir in "${TARGETS[@]}"; do
  # Only install where the Affinity app's parent dir exists (proxy for
  # "this version of Affinity is installed").
  parent="$(dirname "$dir")"
  if [[ -d "$parent" ]]; then
    mkdir -p "$dir"
    rm -rf "$dir/$PLUGIN"
    cp -R "$PLUGIN" "$dir/"
    echo "Installed: $dir/$PLUGIN"
    INSTALLED=$((INSTALLED + 1))
  fi
done

if [[ "$INSTALLED" -eq 0 ]]; then
  echo "" >&2
  echo "WARNING: no Affinity Photo install detected. Plugin not installed." >&2
  echo "Install Affinity Photo 2 or v3 first, then run this script again." >&2
  exit 2
fi

echo ""
echo "Done. Restart Affinity to pick up the new plugin."
echo "If the Filters menu does not show G'MIC, check:"
echo "  - Affinity → Settings → Photoshop Plugins → 'Allow unknown plugins'"
echo "  - 'gmic' binary is installed: 'brew install gmic-qt' or 'brew install gmic'"
```

The script lives at the repo root, gets baked into the release zip,
and is the user-visible install path for non-brew users. It also
serves as the runbook for "what does brew/the cask do underneath"
when we explain the system.

### 4.4 `release/README.txt`

A new file in `release/` (separate from the main repo README so it
can stay terse and not refer to features the user can't see from the
zip):

```text
G'MIC for Affinity Photo — installation
=======================================

1. Make sure gmic is installed:  brew install gmic-qt
   (or just  brew install gmic   if you only need the CLI)

2. Double-click install.command in this folder. macOS may prompt:
   "install.command cannot be opened because it is from an
   unidentified developer." If so:
     a. Right-click install.command  →  Open  →  Open
     b. Or in Terminal:  xattr -dr com.apple.quarantine .

3. Restart Affinity Photo. Look for
   Filters → Plugins → G'MIC → G'MIC…

If the plugin is not detected, check:
  Affinity → Settings → Photoshop Plugins →
    "Allow unknown plugins to be used"  (must be ticked)

Logs: ~/Library/Logs/gmic-affinity.log
Issues: https://github.com/dstrupl/gmic-affinity/issues
```

### 4.5 GitHub Actions release workflow

New workflow `.github/workflows/release.yml`. Triggered on tag push
`v*`. Shape:

```yaml
name: release

on:
  push:
    tags:
      - "v*"

permissions:
  contents: write   # needed to create the release

jobs:
  release:
    runs-on: macos-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: true
          persist-credentials: false
      - name: Toolchain
        run: |
          rustup target add aarch64-apple-darwin x86_64-apple-darwin
      - name: Build release zip
        run: make release RELEASE_VERSION=${{ github.ref_name }} FEATURES=live
      - name: Create GitHub release
        uses: softprops/action-gh-release@v2
        with:
          files: dist/GmicFilter-${{ github.ref_name }}.zip
          fail_on_unmatched_files: true
          generate_release_notes: true
```

The workflow runs after CI has already passed on the same commit
(because we only tag green commits). It uses the existing macOS
runner and the existing build chain — no notarisation step.

### 4.6 What the existing CI workflow does *not* do

The existing `.github/workflows/ci.yml` is untouched by this design.
It still builds the universal bundle on every PR and every push to
`main`. Release adds a second, tag-triggered workflow alongside it.

## 5. The Homebrew tap

### 5.1 Repo layout

A new GitHub repo `dstrupl/homebrew-gmic-affinity` (the `homebrew-`
prefix is mandatory for `brew tap` discovery). Contents:

```text
homebrew-gmic-affinity/
├── Casks/
│   └── gmic-affinity.rb
├── README.md
└── .github/
    └── workflows/
        └── audit.yml          # brew audit --cask on every PR
```

### 5.2 The cask file

```ruby
cask "gmic-affinity" do
  version "0.1.0"
  sha256 "<sha256-of-the-release-zip>"

  url "https://github.com/dstrupl/gmic-affinity/releases/download/v#{version}/GmicFilter-v#{version}.zip"
  name "G'MIC for Affinity Photo"
  desc "Photoshop-compatible filter plugin bridging G'MIC into Affinity Photo"
  homepage "https://github.com/dstrupl/gmic-affinity"

  # Runtime dependency: the plugin shells out to the gmic CLI. The
  # heavier `gmic-qt` cask is a superset that also installs the GUI;
  # we depend on the lighter `gmic` formula and let users pick the
  # GUI separately if they want it.
  depends_on formula: "gmic"
  depends_on macos:   ">= :big_sur"

  # Conditional on Phase 0 step 3. See §3.
  # If quarantine tolerance is confirmed, this line is omitted (default true).
  # If quarantine breaks the plugin, this line is added so brew strips it on install.
  # quarantine false

  artifact "GmicFilter-v#{version}/GmicFilter.plugin",
           target: "~/Library/Application Support/Affinity Photo 2/Plugins/GmicFilter.plugin"
  artifact "GmicFilter-v#{version}/GmicFilter.plugin",
           target: "~/Library/Application Support/Affinity/Plugins/GmicFilter.plugin"

  caveats <<~EOS
    G'MIC for Affinity is installed for Affinity Photo 2 and Affinity v3.
    Restart Affinity to pick up the plugin.

    If Filters → Plugins → G'MIC is missing, enable:
      Affinity → Settings → Photoshop Plugins → "Allow unknown plugins"
  EOS
end
```

Two open uncertainties this cask carries that the implementation will
have to confirm:

1. **Cask DSL: two `artifact` stanzas for the same source path.** The
   intent is "install one copy of the plugin into two locations". The
   `artifact` stanza accepts a single `target:` per call; the docs
   support multiple `artifact` stanzas in one cask. If `brew audit`
   rejects this shape, the fallback is a `preflight` block doing a
   manual `FileUtils.cp_r` to the second target after the first
   `artifact` lays the file down.

2. **Depending on `gmic` vs `gmic-qt`.** The plugin only needs the CLI.
   The current README instructs users to `brew install gmic-qt`. The
   cask depends on `gmic` (smaller, sufficient). Documentation in §6
   reconciles this discrepancy.

If Affinity v3's plugin folder turns out to be something other than
`~/Library/Application Support/Affinity/Plugins`, the second `artifact`
target string changes. That string is the only thing in this cask that
depends on Phase 0 step 2.

### 5.3 Tap CI

A single workflow:

```yaml
name: cask audit

on:
  push:
    branches: [main]
  pull_request:

jobs:
  audit:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - name: brew audit
        run: brew audit --cask Casks/gmic-affinity.rb
      - name: brew style
        run: brew style Casks/gmic-affinity.rb
```

This is the same gate the central `homebrew-cask` repo uses on PRs.
Catching policy regressions on the tap means we won't be caught flat-
footed if we later want to submit to the central repo.

### 5.4 Per-release tap update procedure

After the project's release workflow uploads
`GmicFilter-vX.Y.Z.zip` to GitHub Releases:

1. Compute the artifact SHA256:
   `curl -sL https://github.com/.../releases/download/vX.Y.Z/...zip | shasum -a 256`
2. Open a PR against `dstrupl/homebrew-gmic-affinity` updating
   `version` and `sha256`.
3. `brew audit --cask` on the PR; merge if green.
4. Users get the update on next `brew upgrade --cask`.

Optional automation (not in v0.1 scope): a GitHub Action in the
*project* repo that, on release publish, opens that tap PR
automatically. Deferred until release cadence justifies it.

## 8. Risks (have a plan for each)

| # | Risk                                                                                       | Severity | Plan                                                                                                                                                          |
|---|--------------------------------------------------------------------------------------------|----------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | Affinity v3 does not load the current bundle at all                                        | **High** | Phase 0 step 2 catches this before any code change. If it fires, v3 compatibility becomes a separate spec; v0.1 may ship as Affinity Photo 2 only.            |
| 2 | Affinity refuses to load a quarantined bundle (path C dies)                                | **High** | Phase 0 step 3 catches this. Fallback: ship path D only; tap (if shipped) instructs `--no-quarantine`; reopen Apple Dev decision.                             |
| 3 | The brew cask DSL doesn't accept two `artifact` stanzas with the same source               | Medium   | Implementation falls back to a `preflight` block that does the second copy manually. `brew audit` will tell us in CI.                                          |
| 4 | The v3 plugins folder path is not `~/Library/Application Support/Affinity/Plugins`         | Medium   | Phase 0 step 2 establishes the real path. Both the Makefile default and the cask `artifact` target are updated accordingly.                                    |
| 5 | `gmic` formula in homebrew-core is renamed / deprecated / merged into `gmic-qt`            | Low      | Cask `depends_on` is one line; we update it. The CI `brew audit` on the tap surfaces formula renames as a hard failure on next `brew tap upgrade`.            |
| 6 | First-install Gatekeeper warning on the manual path scares users away                       | Low      | `install.command` strips quarantine on itself with `xattr -dr`. `release/README.txt` documents the right-click → Open workaround as a one-time step.            |
| 7 | GitHub Actions release workflow flakes (network, runner, signing)                          | Low      | The workflow is idempotent (rerun the failed job; `softprops/action-gh-release@v2` replaces the asset if the release exists). Manual fallback: `gh release create` locally with the same artifact. |
| 8 | Users on macOS < Big Sur try to install                                                    | Low      | Cask declares `depends_on macos: ">= :big_sur"`. `install.command` could also check `sw_vers -productVersion`, but the bundle's `LSMinimumSystemVersion` already gates this. |
| 9 | Tap repo and project repo drift (cask version pointing at a missing release)                | Low      | The tap CI's `brew audit` catches broken URLs. Cask PRs are opened from a release-day runbook (§5.4) keyed off the actual release artifact.                    |

## 10. Implementation milestone ordering

Designed so the highest-risk pieces (§8 #1 and #2) are proven first.

1. **Phase 0 — empirical de-risking** (§3). One afternoon, no code
   changes. Resolves the two design contingencies.
2. **Both-Affinity install** (§4.1). Smallest code change; lets the
   developer flow already match the user flow.
3. **`install.command` + `release/README.txt`** (§4.3, §4.4). The
   manual install path. Unblocks shipping path D even if path C dies.
4. **`make release` + local end-to-end dry run** (§4.2). Verify the
   zip layout, the SHA256 stability, the manual install on a fresh
   user account.
5. **Release GitHub Actions workflow** (§4.5). Tag-driven release
   pipeline. First tag: `v0.1.0-rc.1`, exercises everything.
6. **Documentation refresh** (§6). README restructure, PRD update,
   IMPLEMENTATION_NOTES.md §11.
7. **Homebrew tap repo + cask file + tap CI** (§5). Land alongside
   the first real `v0.1.0` tag.
8. **End-to-end install verification on a fresh Mac account** —
   manual; one paragraph of notes appended to the implementation
   plan's self-review section.

Milestones 2–4 can begin even if Phase 0 step 3 (quarantine
tolerance) hasn't been run yet. Milestone 7 hard-depends on Phase 0
step 3 because the cask shape changes based on its outcome.
